# RootCause Stream

> 센서 기록으로 판단이 안 될 때, **사람에게 사진을 요청하는** 설비 진단 Agent.

2026년 LLM/VLM 기반 서비스 개발 프로젝트.

## 무엇을 하나

공장 설비에 이상이 생기면 알람이 수십 개씩 쏟아진다. 대부분은 원인이 아니라 결과다.
현장 엔지니어는 기록과 매뉴얼을 오가며 원인을 좁히고, 기록만으로 모르겠으면 **직접 가서 본다.**
이 Agent는 그 마지막 단계, 즉 "가서 봐야겠다"는 판단까지 한다.

```
알람 ─▶ 가설 세우기 ─▶ 도구로 증거 모으기 ─▶ 센서로 안 갈리면 촬영 요청 ─▶ 사진 판독 ─▶ 근거를 인용한 결론
                       (공정 데이터 · 매뉴얼     (무엇을 찍을지 +             (정상 샘플과
                        · 도면 · 과거 사례)       "이게 보이면 H2" 사전 선언)    나란히 비교)
```

| 장치 | 왜 |
|---|---|
| **촬영 요청 = 비동기 중단점** | 작업자가 사진을 찍기까지 몇 분이 걸리고, 응답이 없을 수도 있다. 진단 상태를 저장해 두고 사진이 오면 이어서 진행한다 (`app/agent/loop.py`) |
| **사전 선언** | 사진을 보기 전에 "이게 보이면 어느 가설을 지지한다"를 적는다. 사진을 본 뒤 결론과 어긋나면 **한 번 되묻는다** (`app/agent/declaration.py`) |
| **정상 샘플 비교** | 같은 설비·같은 설정에서 합격한 용접 사진과 나란히 보고 판독한다 (`app/agent/tools/photo.py`) |
| **인용 강제** | 결론에는 근거 증거를 인용해야 하고, 없는 증거를 인용하면 거부한다 (`app/agent/schemas.py`) |

## 핵심 결과 — 사진이 있어야 잡히는 결함

실제 용접 사진과 파괴시험 판정이 함께 공개된 데이터셋으로 쟀다.
데이터셋: [RSW Insights](https://doi.org/10.17632/rwh8kjzdch.3), CC BY 4.0.
사건은 날림(expulsion) 29건과 같은 설정값의 정상 용접 29건이다.
날림은 공정 신호만으로는 거의 구별되지 않는다. 자세한 내용은 [eval/RESULTS_TIER_E.md](eval/RESULTS_TIER_E.md)에 있다.

| | 정확도 | 날림을 날림으로 |
|---|---:|---:|
| 규칙 (최대 전류 > 같은 설정 p90) | 50% | 7% |
| 지도학습 분류기 (판정 라벨 수백 개로 학습) | 57% | 17% |
| Agent (sonnet) — 사진 없음 | 45% | **0%** |
| Agent (sonnet) — 그 용접의 사진 | 53% | 24% |
| Agent (sonnet) — 사진 + 정상 샘플 + 사전 선언 대조 | 55% | 21% |
| Agent (sonnet) — 위 + **뒷면도 요청 가능** | **67%** | **41%** |
| ↳ 같은 조건, **다른 용접의 사진으로 바꿔치기** | 29% | 3% |

- **사진이 없으면 날림을 하나도 못 잡는다.** 사진이 있을 때 sonnet이 더 잡은 날림은 7건, 덜 잡은 것은 0건이다 (p=0.016).
- **Agent는 사진 내용을 근거로 쓴다.** 진짜 사진과 바꿔치기 사진을 사건별로 짝지어 비교했다. 진짜 사진에서만 맞힌 것이 24건, 바꿔치기에서만 맞힌 것이 2건이다 (p=0.00001). 바꿔치기 사진을 주면 정확도가 29%로 떨어진다.
- **무엇을 찍을지 Agent가 정한다.** 작업자가 시편의 어느 면이든 찍을 수 있다고만 알렸다. 그러자 Agent는 58건 중 57건에서 스스로 뒷면도 요청했다.
  날림을 잡는 비율이 앞면만 쓸 때의 두 배가 됐다 (21% → 41%). 정확도는 55% → 67%로 올랐다 (p=0.065, 경계).
- **날림은 아직 절반 넘게 놓친다.** 단계마다 병목을 찾아 하나씩 풀었다.
  1. 판독기가 미세한 흔적을 못 봄 → 정상 샘플과 비교하게 하자 판별력이 +3%p에서 +35%p로 올랐다.
  2. Agent가 판독을 무시함 → 사전 선언 대조로 사진을 따르게 했다.
  3. 앞면에 흔적이 없는 날림 → 뒷면 촬영을 허용하자 Agent가 스스로 요청했다.
  4. 남은 병목: Agent가 선언하는 관찰이 여러 특징을 한 문장에 묶는다 ("튄 금속, 분화구 **또는 변색**"). 그래서 판독이 부정확해진다.
- ⚠️ 날림은 데이터셋 전체에 31건뿐이라, 같은 58건으로 여러 설계를 쟀다. 그래서 설계 반복은 여기서 멈췄다.
- ⚠️ 2026-11-22 정정: 한 라운드의 증거가 여러 개면 마지막 것만 Agent에게 보이는 버그가 있었다. 고친 뒤 다시 잰 값이 위 표다.
  haiku 측정은 영향이 커서 쓰지 않는다 ([정정 절](eval/RESULTS_TIER_E.md)).

## 공장 데이터 — 도구를 골라 쓰는 진단, 그리고 규칙과의 비교

[KAMP](https://www.kamp-ai.kr) 저항 점용접 공정 데이터로 도구 선택과 해석을 쟀다. 채점은 opus로 했다.

| 근본원인 정확도 | Agent | 알람만 보는 베이스라인 | 규칙 한 줄 |
|---|---:|---:|---:|
| A 조용한 수준 이동 (3건) | 89% (haiku) · 100% (sonnet) | – | 100% |
| C 알람 폭주 (8건) | 92% | 4% | 100% |
| B 주입 고장, 주 변수 (7건) | 86% | 86% | 100% |

- **발견 — 이상의 정체는 기록 재활용이었다** ([docs/14](docs/14-data-reuse-finding.md)).
  기록의 97.2%가 다른 작업일과 수백 행씩 연속으로 똑같다. 순서를 섞은 대조에서는 최대 2행이다.
  설비 고장이 아니라 데이터 수집 문제다.
- **정직한 위치.** 이 데이터에서 결정적 신호("다른 작업일과 연속 일치 비율")는 사람이 설계한 것이고, 규칙 한 줄도 Agent만큼 맞힌다.
  - 그 신호를 빼고 원시 기록과 SQL만 주었을 때 Agent는 재활용을 스스로 찾지 못했다. sonnet도 0%였다 ([docs/15](docs/15-agent-writes-sql.md)).
  - 그래서 공장 데이터는 "도구를 골라 쓰고 해석하는 진단"의 예시로 두었다. LLM·VLM의 고유한 기여는 위의 사진 결과로 주장한다.
- 측정 중 정답 누출 2건을 찾아 고친 뒤 다시 쟀다 ([docs/15](docs/15-agent-writes-sql.md)). 누출 덕을 본 쪽은 오히려 베이스라인이었다.

## 실행

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000    # 관제 화면 http://localhost:8000
```

- 사건을 고르면 Agent가 진단을 시작한다. 촬영 요청이 오면 QR로 휴대폰에서 찍어 올리거나, 준비된 사진으로 응답한다.
- 실제 용접 사건(E-323 등)에서는 "이 용접의 사진"과 "다른 용접(대조)" 중에서 고를 수 있다.
- 시연 사건 4건은 잘 되는 사건으로 골랐다. 전체 성능은 위 표와 같다.
- 녹화 재생: `/?replay=e323-faces` (날림 — 앞면·뒷면 촬영 요청 → 정상 샘플과 비교 판독 → 선언 대조 → 결론), `/?replay=a25-timeout`. 실제 실행 기록을 시간만 압축해 보여준다 (`scripts/record_demo.py`).
- 진단은 sonnet, 사진 판독은 haiku로 한다. `claude -p` CLI를 쓰므로 API 키가 필요 없다.
- 평가 실행:
  - `python -m eval.run_tier_e`: 사진 실험
  - `python -m eval.run`: 공장 데이터
  - 원 자료는 `eval/results/`에 있다.

**데이터.** KAMP 원본과 제조사 매뉴얼은 재배포 권한이 확인되지 않아 레포에 올리지 않았다. 받는 방법은 `data/raw/README.md`와 `data/manuals/SOURCES.md`에 적었다.
용접 사진은 CC BY 4.0이며, 실험에 쓴 것만 출처와 함께 올렸다 (`data/photos/tier_e/ATTRIBUTION.md`).
