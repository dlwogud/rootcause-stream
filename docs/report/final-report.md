## 1. 요약

- 주제: 센서 기록으로 판단이 안 될 때 현장 작업자에게 사진을 요청하는 설비 진단 Agent
- 핵심 주장 (범위를 넘지 않는다)
  1. 공정 신호만으로 거의 구별되지 않는 결함(용접 날림)을, Agent는 사진이 없으면 하나도 잡지 못하고 사진이 있으면 일부 잡는다.
     sonnet 기준 0% → 24%, p=0.016 (`model_comparison.json`)
  2. Agent는 사진 내용을 실제 근거로 쓴다. 진짜 사진 대 바꿔치기 사진은 64% 대 36%이고, 진짜에서만 맞힌 것이 15건, 바꿔치기에서만 맞힌 것이 0건이다 (p=0.0001, run #83)
  3. Agent가 무엇을 찍을지 스스로 정한다. 어느 면이든 찍을 수 있다고만 알리자 55건 중 54건에서 뒷면을 요청했다. 정확도는 앞면만 쓸 때 55%에서 64%로 올랐지만 유의하지 않다 (p=0.27).
  4. 전체 정답률은 64%로, 규칙(50%)·지도학습 분류기(57%)보다 높지만 유의성은 따로 검정하지 않았다. 병목을 단계별로 찾아 풀었고, 남은 병목을 밝혔다.
  5. 공장 데이터(KAMP)에서는 사람이 설계한 신호를 쓰면 규칙 한 줄도 Agent만큼 맞힌다. 신호 없이 원시 데이터와 SQL만 주면 Agent는 결함을 스스로 찾지 못했다.
- **[채울 것]** 한 문단 초록 (마지막에 쓴다)

## 2. 문제와 동기

- 알람 폭주: 대부분은 결과다. 원인은 기록·매뉴얼·현장 확인을 오가며 찾는다 (`docs/01-overview.md`)
- 왜 LLM·VLM인가: 촬영 지시 생성("무엇을 찍으면 어떤 가설이 갈리는가"), 사진 판독, 비정형 매뉴얼·도면 검색
- 왜 이것이 어려운가: 사진은 수 분 뒤에 오거나 오지 않는다. 사진을 본 뒤 해석을 바꾸는 사후 합리화가 생긴다.

## 7. 한계와 정직성

- **같은 58건을 여러 설계 반복에 썼다.** 날림은 31건뿐이라 새 시험 세트를 만들 수 없다.
- **LLM 출력의 실행 간 변동**이 크다. 같은 사건·같은 프롬프트에서도 사진 요청 여부가 달라진다.
  2026-11-20 재측정: 15건을 다시 돌렸을 때 사진 요청 13 → 12건, 정답 6 → 6건으로 전체 비율은 유지됐다.
  그러나 사건 단위로는 바뀐다. E-317은 측정 때 4번 모두 사진을 요청했지만, 같은 날 다시 돌린 4번은 모두 요청하지 않았다
  (입력 프롬프트는 글자 단위로 같았다). 시연 녹화는 사진을 요청한 실행을 쓴다 — 기록을 고른 것이다.
- 다른 설비(실험실)의 데이터다. 공장 사건과 섞어 말하지 않는다.
- 측정 중 고친 것: 정답 누출 2건, Tier A 정답 정정, 실행기 버그 — 모두 고친 뒤 다시 쟀다.
