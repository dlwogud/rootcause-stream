# 14. 발견 — 복제 라벨 밖의 기록도 대부분 재활용이었다

> 2026-11-17 · 재현: `.venv/bin/python scripts/91_cross_day_audit.py` → `eval/results/cross_day_audit.csv`

## 어떻게 알게 됐나

발표 시연을 녹화하려고 웹 서비스로 Tier A 사건(2020-03-25)을 실제로 돌렸다. Agent의 결론은 다음과 같았다.

> *"The 'low force' level shift is a data-acquisition problem, not a physical force change.
> About half of this window (a run of 260 consecutive records, all four process values
> identical) is reproduced from another workday."*

당시 Tier A의 정답은 **"센서로 원인 특정 불가 → 추가 관측 필요"**였기 때문에 처음에는 오답으로 보였다.
Agent가 근거로 든 것은 `query_timeseries`가 데이터에서 직접 계산하는 `repeat_signals`였다
(`cross_day_run_fraction = 0.503`). 이 값이 무엇을 가리키는지 직접 확인했다.

## 확인한 것

| 항목 | 값 |
|---|---|
| 전체 기록 | 11,939행, 서로 다른 (가압력·전류·전압·시간) 튜플 1,574종, 최빈 튜플 0.5% |
| 선행 프로젝트의 복제 라벨 | 800행 덩어리 × 4개 작업일 = **26.8%** |
| 다른 작업일과 **30행 이상 연속 동일**한 기록 | **97.2%** |
| 복제 라벨도 재활용도 아닌 기록 | **329행 (2.8%)**: 3/24 244행, 4/7 83행, 3/25 2행 |
| 다른 작업일과 공유하는 최장 연속 수열 | **400행 이상** (탐색 상한) |
| 대조: 작업일 안에서 행 순서를 무작위로 섞었을 때 | **2행** |

우연으로는 다른 날과 3행만 연속으로 겹쳐도 나오지 않는다. 그런데 실제 데이터는 수백 행이 통째로 겹친다.
따라서 이것은 설비가 만든 현상이 아니라 **기록을 재활용하거나 반복해서 적재한 결과**다.

3/25를 예로 들면, 복제 라벨을 뺀 552행 가운데 다음 두 구간이 다른 작업일에 그대로 있다.
- idx 2–261: 3/27 idx 466–725, 3/31 idx 456–715와 동일
- idx 1071–1330: 3/24·3/26·3/30·4/2·4/7과 동일

두 구간 모두 해당 날짜의 800행 복제 덩어리 **바로 옆**에 붙어 있다.
선행 프로젝트의 탐지가 복제 덩어리의 경계를 좁게 잡았던 것으로 보인다.

## 무엇이 바뀌나

| | 이전 | 이후 |
|---|---|---|
| **Tier A 정답** | 원인 특정 불가 → 추가 관측 필요 (보류형) | **데이터 수집 계통 이상: 기록 재활용** |
| Tier A 주 지표 | M9 (보류 + 가르는 관측) | **M1** (근본원인, LLM-as-Judge) |
| Tier C 정답 | 데이터 수집 계통 이상 | 그대로. 근거는 더 강해졌다 |
| Tier B (합성 주입) | — | 영향 없음 |
| 선행 프로젝트 "관리도 3/3, p=0.0179" | 이상일에 진짜 공정 차이가 있다는 근거 | 비교 대상인 '안정일'도 재활용 기록이다. **작업일 중앙값의 차이는 어떤 덩어리로 조립됐는지의 차이**일 수 있다. 공정 변화의 근거로 쓰지 않는다 |

## 지키는 원칙

- **Agent 프롬프트는 바꾸지 않았다.** 새 정답을 알게 된 뒤 프롬프트를 고치면 정답에 맞춘 튜닝이 된다.
  같은 Agent, 같은 도구로 정답지만 바꿔 다시 측정한다.
  - 참고로 수준 이동 사건의 시작 프롬프트(`kickoff_level_shift.md`)는
    "운전 조건 변화(레시피·설정값·공구)인가"를 먼저 묻는다. 새 정답의 반대 방향으로 기운 셈이다.
    Agent는 이것을 이기고 데이터 문제를 짚었다.
- **이전 Tier A 수치(베이스라인 0% → Agent 100%)는 폐기한다.** 당시 지표(M9)는 "요청했는가"만 봤다.
  정답 자체가 틀렸으므로 그 숫자는 아무것도 입증하지 않는다.
- 이전 실행은 결론 원문을 저장하지 않아 다시 채점할 수 없었다.
  이제 `eval/run.py`가 `_root_cause`를 남긴다.

## 의미

사람이 만든 정답 라벨(선행 프로젝트)이 놓친 데이터 결함을, Agent가 **데이터에서 계산한 신호를 근거로** 먼저 짚었다.
정답지를 의심하게 만든 것이 평가 대상이었다는 점이 이 프로젝트에서 가장 강한 사례다.
동시에, 사진 루프가 실제 데이터에서 효과가 있다는 근거는 이번 정정으로 사라졌다.
사진 루프는 **구현과 동작(웹 E2E)까지만 주장**한다.
