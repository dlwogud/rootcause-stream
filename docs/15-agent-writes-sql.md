# 15. 실험 — Agent가 직접 SQL로 조사하면 기록 재활용을 찾는가 (음성 결과)

> 2026-11-19 · run #57·#60·#64 (haiku) · #71·#72 (sonnet, 채점 opus) · 도구 `app/agent/tools/sql.py`

## 왜 했나

규칙 비교(`scripts/94_rule_baseline.py`) 결과, 공장 데이터(A·B·C)에서는 **규칙 한 줄이 Agent와 같거나 더 잘 맞혔다**.
- 규칙: "다른 작업일과 연속 일치하는 비율 ≥ 30% → 데이터 이상"
- 결정적 신호(`cross_day_run_fraction`)를 사람이 설계한 코드가 미리 계산해서 주기 때문이다.
- 그렇다면 LLM이 기여한 것은 그 숫자를 읽은 것뿐이다.

그래서 이 신호를 빼고 **원시 기록 테이블과 SQL**만 주었다.
무엇을 확인할지 Agent가 스스로 정해야 한다.

## 조건

- `query_timeseries`(신호를 미리 계산하는 도구)를 끄고, `query_sql`을 켰다.
  - 테이블: `records(workday, seq, ts, force, current, voltage, weld_time)` — 모든 작업일의 모든 기록, 라벨 없음
- 신호 해석 설명을 뺐다 (`--no-signal-guide`).
- 스텝 한도는 9에서 **12로 늘렸다** — 질의로 탐색할 여유를 주기 위해서다.
- 나머지 도구(매뉴얼·도면·사례)는 그대로 두었다.

**조사는 가능했다.** 다른 작업일과 연속으로 겹치는 기록 수를 세는 질의는 한 문장이고, 실행에 0.02초가 걸린다.

## 결과 (근본원인 정확도)

| | 미리 계산한 신호 (haiku) | SQL만 — haiku | SQL만 — sonnet |
|---|---:|---:|---:|
| A 조용한 수준 이동 (3건) | 89% (×3) | 11% (×3) | **0%** (×2) |
| C 알람 폭주 (8건) | 92% (×3) | 21% (×3) | **0%** (×2) |
| B 주입 고장 (주 변수, 7건) | 86% | 100% | — |

## 무엇을 찾았고 어디서 틀렸나

Agent는 질의를 직접 써서 단서까지는 찾았다.
- "3/25는 순번 271–999가 통째로 비어 있다"
- "291행짜리 고압 기록 덩어리가 3/25·3/27·3/31·4/3에 똑같이 있다"

그러나 결론은 대부분 **"설비가 반복적으로 고압 운전 모드로 전환했다"**였다.
- sonnet은 22번 모두 이렇게 해석했다.
- 실제 측정값이 수백 행에 걸쳐 같은 순서로 소수점까지 똑같이 반복되는 것은 물리적으로 불가능하다.
  Agent는 그 한 걸음을 내딛지 않았다.
- 더 강한 모델(sonnet)이 오히려 더 확신 있게 "운전 모드"로 결론 냈다.

## 결론

- 이 데이터에서 기록 재활용을 가려낸 것은 **사람이 설계한 분석 신호**였다. LLM의 역할은 그 신호를 읽고 해석하는 것이었다.
- LLM에게 원시 데이터와 SQL을 주어도 이 결함을 **스스로 발견하지 못했다**. 모델을 키워도 마찬가지였다.
- 그래서 프로젝트의 중심을 **LLM·VLM만 할 수 있는 일**로 옮긴다. 즉, 사진을 요청하고 읽어서 규칙이 못 잡는 결함을 잡는 일(Tier E)이다.
  공장 데이터는 "도구를 골라 쓰고 해석하는 진단"의 예시로 위치를 낮추고, 규칙과 동등하다는 사실을 함께 적는다.
