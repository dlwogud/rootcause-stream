# 01. 서비스 개요 및 핵심 가치

## 문제

설비에 이상이 생기면 알람이 수십~수백 개 동시에 터진다(alarm flood). 신입 작업자는 어느 알람이 **원인**이고 어느 것이 **결과(파생 알람)**인지 구분할 수 없다. 베테랑의 암묵지에 의존하는 영역이다.

그리고 더 근본적인 문제가 있다.

> **센서 데이터만으로는 원인을 확정할 수 없다.**

레거시 설비는 계측이 반쪽이다. 저항점용접기를 예로 들면, 공정 데이터로 측정되는 것은 가압력·전류·동저항·입열량 4개뿐이다. 그러나 품질 이상의 실제 원인 상위 항목은 다음과 같다.

| 원인 | 센서로 측정되는가 |
|---|---|
| 전극 팁 마모·오염 | ❌ 육안 점검 |
| 가압 실린더 공압 저하 | △ 아날로그 게이지 |
| 냉각수 유량 저하 | △ 아날로그 유량계 |
| 전극 정렬 불량 | ❌ 육안 점검 |
| 데이터 수집 계통 이상 | ❌ (오히려 정상처럼 보인다) |

**즉 원인의 절반 이상이 "현장에 가서 눈으로 봐야 하는 정보"다.** 기존 이상탐지 시스템은 "이상입니다"까지만 말하고 멈춘다.

## 핵심 가치

RootCause Stream은 Agent가 **자기 지식의 공백을 인식하고, 물리 세계에 있는 사람을 센서로 사용한다.**

1. 알람 폭주를 근본원인 1개로 수렴시킨다 (파생 알람 제거)
2. 센서로 구분되지 않는 가설은 **매뉴얼 도면**을 읽어 좁힌다
3. 도면으로도 안 갈라지면 **작업자에게 촬영을 요청**한다 — "어떤 사진이 어떤 가설을 가르는지" 계산해서
4. 사진을 VLM으로 판독해 가설을 **확정**한다
5. 확정된 원인에 대해 매뉴얼의 **플로우차트 이미지를 실행 가능한 조치 단계로 변환**한다
6. 작업자 조치 결과를 사례로 적립해 다음 유사 알람에서 재사용한다

## 핵심 사용자

| | |
|---|---|
| 1차 | 설비 운전자 / 관제실 신입 — 알람을 받고 조치해야 하는 사람 |
| 2차 | 설비 보전 담당 — 사례 축적의 수혜자 |
| 비사용자 | 데이터 사이언티스트 (이상탐지 모델 개선은 이 서비스의 목표가 아니다) |

## 이용 시나리오

```
14:03  작업일 중반, 가압력 중위수가 하향 이동 시작
14:03  관리도 + kNN 이상점수 동시 발화 → 알람 47건 버스트
14:03  Flink가 버스트 감지 → Incident #128 생성
14:03  Agent 가설 3개 생성
         H1 전극 팁 마모 (확률 0.42)
         H2 가압 실린더 공압 저하 (0.35)
         H3 데이터 수집 계통 이상 (0.23)
14:04  Agent: 센서 시계열 추가 조회 → H3 약화 (0.23 → 0.09)
14:04  Agent: P&ID 도면 조회 → 공압 계통은 2개 실린더 공용 → H2라면 반대편 건도 이상해야 함
         → 반대편 데이터 조회 → 정상 → H2 약화 (0.35 → 0.14)
14:05  Agent: H1 vs H3 를 센서로 더 가를 수 없다고 판단
         → 촬영 요청 생성
           ① 상부 전극 팁 선단 근접 사진 (H1 판별)
           ② 가압 실린더 공압 게이지 (H2 잔여 확인)
14:05  작업자 휴대폰에 알림 → QR/링크로 업로드 페이지
14:08  사진 2장 업로드
14:08  VLM 판독
           ① 팁 선단 버섯형 변형 + 표면 산화 → 마모 진행 (신뢰도 높음)
           ② 게이지 바늘이 녹색 구간 → 정상
14:08  Agent: H1 확정 (0.42 → 0.91)
14:08  조치 카드 생성 (매뉴얼 플로우차트 기반)
           1. 설비 정지 및 전원 차단
           2. 전극 팁 드레싱 또는 교체 (매뉴얼 4-3절, p.37)
           3. 교체 후 시험 타점 5점, 동저항 편차 확인
           4. 확인 포인트: 가압력 중위수가 기준 범위로 복귀하는가
14:20  작업자 조치 완료 피드백 → 사례 #0041 적립
```

**다음에 같은 유형이 발생하면 Agent는 3단계(도면 조회)를 건너뛰고 사례 #0041을 먼저 제시한다.**

## 목표 / 비목표 / 반목표

**목표**
- 알람 버스트 → 근본원인 1개 수렴
- 센서로 불가능한 판정을 도면·사진으로 해결
- 각 LLM/VLM 구성요소의 기여도를 수치로 증명 (ablation)

**비목표**
- 이상탐지 모델 자체의 성능 개선 (선행 프로젝트에서 이미 다룸)
- 실시간 제어 / 설비 자동 정지 (사람의 조치를 전제로 한다)
- 다품목 설비 범용화 (검증은 RSW 1종)

**반목표 (이렇게 되면 기술적으로 작동해도 실패)**
- 기술을 10개 넣었지만 각각의 기여를 측정하지 못한 상태
- 정답 라벨을 스스로 심어놓고 찾아낸 상태
- 시연에서 미리 준비된 사진만 동작하는 상태 (현장 촬영 시연이 안 되면 핵심 주장이 증명되지 않는다)
